Skills: procedimientos que el equipo comparte

Qué es una skill

Un paquete de instrucciones (y opcionalmente scripts, plantillas y ficheros de referencia) que el agente carga sólo cuando la tarea lo requiere.

  • Se escribe una vez y la usa todo el equipo: vive en el repositorio y se revisa como el código.
  • Se carga bajo demanda: no infla el contexto de todas las conversaciones.

Lo que NO es

  • Un prompt gigante que pegas siempre: eso es ruido permanente.
  • Un documento de 30 páginas que nadie lee: una skill es una receta, no un manual.
skills/
  revisar-pr/
    SKILL.md          ← instrucciones + cuándo usarla
    checklist.md      ← referencia
    scripts/lint.sh   ← herramienta auxiliar
  migrar-a-python3/
    SKILL.md
  informe-mensual/
    SKILL.md
    plantilla.md
Anatomía habitual de SKILL.md: un encabezado con nombre + descripción (es lo que el agente lee para decidir si la carga) y el cuerpo con el procedimiento paso a paso, criterios de aceptación y ejemplos.
  • El truco de las skills es la descripción: debe decir claramente cuándo aplicarla, o nunca se cargará.
  • Comparar con "runbooks" de operaciones: mismo concepto, ahora legible por una máquina.

Escribir una buena skill (y una mala, para comparar)

Mala skill

nombre: ayuda
descripción: ayuda con el código

Haz un buen trabajo, revisa el código
y arregla los problemas importantes.
Usa las mejores prácticas.

Vago, sin criterios, sin pasos, sin verificación. El agente hará lo que quiera.

Skill útil

nombre: revisar-pr
descripción: Revisa un PR antes de pedir
  revisión humana. Úsala cuando el usuario
  diga "revisa este PR" o "prepara el PR".

1. Ejecuta: npm test && npm run lint
2. Si falla → corrige y repite (máx. 3 vueltas)
3. Comprueba contra checklist.md
4. Resume: qué cambiaste y qué debe
   revisar un humano
No toques migraciones ni ficheros de
configuración de despliegue.
Cinco ingredientes de una skill que funciona: cuándo usarla · pasos concretos con comandos · criterio de terminado · límites explícitos · lugar donde dejar constancia.
  • Regla: si no puedes escribir el criterio de "terminado" en una línea, la tarea no está lista para delegarse.

Cómo se comparten y evolucionan (o mueren)

Organización que funciona

  • Un repositorio de skills del equipo (o una carpeta en el repo principal), versionado con git.
  • Una carpeta por skill, con su fichero de instrucciones y sus recursos; nombres claros.
  • Dueño por skill. Sin dueño, se pudre. E instalación trivial: clonar y listo.
  • Un índice con descripción, dueño y fecha de última revisión.

Reglas de convivencia

  • Se revisan como código: PR, una persona que las pruebe antes de mezclar.
  • Cambios anunciados: si una skill cambia de criterio, avisar (aquí se rompen confianzas).
  • Borrar las que ya no se usan. Veinte skills activas son mejores que doscientas olvidadas.
  • Prohibido meter secretos, credenciales o datos de clientes dentro de una skill.

Antipatrones del catálogo

  • Una persona con 40 skills que nadie más usa.
  • Skills de 300 líneas que nadie lee: ahí se cuelan instrucciones peligrosas.
  • Copiar skills de terceros sin leerlas: son código, no texto decorativo.
  • Medirlas por número y no por uso: ¿cuántas veces se ha usado y qué ha ahorrado?
  • Comparar con los scripts internos: mismo destino si nadie los mantiene. La diferencia es que una skill también documenta el proceso.

El fichero de convenciones del proyecto

Qué poner (y qué no)

  • Sí: comandos exactos (build, test, lint, migraciones), arquitectura en 5 líneas, convenciones de nombres, idioma de los commits, prohibiciones ("no toques /migrations" sin pedir permiso).
  • Sí: dónde mirar para cada tipo de tarea (mapa del repo).
  • No: la historia del proyecto, la filosofía, la orgánica del equipo, ni párrafos motivacionales.
  • No: cosas que el código ya dice (el agente lo puede leer).
  • Regla: si algo falla dos veces, se añade una línea aquí.

Memoria y decisiones: lo que hay que recordar entre sesiones

El problema

Cada sesión empieza en blanco. Sin un mecanismo, repites el mismo contexto cada vez y el equipo aprende nada.

La solución: dos tipos de memoria

  • Decisiones (tipo ADR): "usamos Postgres, no Mongo, por X". El agente debe respetarlas siempre.
  • Aprendizajes y notas: descubrimientos, trampas conocidas, patrones del proyecto.
# decisión: ADR-014 cola de trabajos
Fecha: 2026-09-02
Estado: aceptada

Contexto: los informes tardan 40 min y bloquean
la API.
Decisión: cola en Redis + workers propios.
Consecuencias: +1 servicio; reintentos idempotentes.
Alternativas descartadas: cron por cliente.
Un ADR no es burocracia: es el prompt más barato del mundo. Cien palabras que evitan que la IA (y el nuevo compañero) vuelva a proponer lo que ya se descartó.
  • Idea: la memoria del agente debería ser mayoritariamente los ficheros del repositorio, no bases de datos opacas.

Escribir la decisión antes de codificar

Especificar primero, en serio

  1. Objetivo: qué problema resuelve, en una frase.
  2. Criterios de aceptación: cómo sabremos que está bien (comprobables).
  3. Restricciones: rendimiento, compatibilidad, normativa, presupuesto.
  4. Decisiones abiertas: lo que aún no sabemos y hay que resolver.
  5. Plan: los pasos, en orden, con verificación en cada uno.

Con un agente, esto no es papeleo: es la diferencia entre 3 vueltas y 30.

Por qué funciona mejor con IA que sin ella

  • El agente no adivina tu intención: sigue lo que está escrito.
  • Puedes revisar el plan antes de gastar tokens en la ejecución.
  • Los criterios de aceptación se convierten en tests de forma natural.
  • Si la sesión se pierde, otro (o tú mañana) retoma el trabajo.
Antipatrón extendido: "hazme una app de gestión de tareas" y esperar magia. Con un objetivo difuso el agente produce un borrador difuso, y luego nadie sabe por qué se decidió cada cosa.
  • Conectar con metodologías conocidas (spec-driven, design docs): no es nuevo, es la misma disciplina con un ejecutor incansable enfrente.
  • Meme de descanso: se pasa rapido, sin comentario. Si no hay tiempo, salta con →.

Prompts que funcionan: la anatomía en seis piezas

PiezaPregunta que respondeEjemplo
Rol y objetivo¿Quién eres y qué resultado quiero?"Actúa como revisor de código. Quiero detectar bugs antes del merge."
Contexto¿Qué necesitas saber?"Este módulo gestiona facturación; los importes son en céntimos."
Entradas¿Con qué trabajas?Los ficheros, el error, el ejemplo, la captura.
Restricciones¿Qué límites hay?"Sin dependencias nuevas. Compatible con Python 3.11. No toques migraciones."
Formato de salida¿Cómo quiero la respuesta?"Tabla con: fichero, línea, problema, gravedad, propuesta."
Verificación¿Cómo comprobamos que es correcto?"Ejecuta los tests y muéstrame la salida. Si no puedes, dilo."
Si te falta tiempo, prioriza objetivo + criterio de terminado + verificación. Con eso solo ya estás por encima de la media.

Truco del ejemplo

Un ejemplo de entrada y salida esperada ahorra párrafos de explicación. Es la forma más barata de especificar formato y estilo.

  • Hacer el ejercicio en vivo: convertir una petición mala en una buena con las seis piezas.

El stack completo: cómo encajan las piezas

Modelo

El motor. Se elige por tarea y se cambia cuando conviene.

Harness

Bucle, herramientas, permisos, contexto. Decide lo que es posible.

Skills + convenciones

El conocimiento del equipo, versionado en el repo.

MCP / integraciones

Los sistemas reales: tickets, datos, infraestructura, nube.

Repositorio (convenciones, skills, ADRs)+ Harness+ Modelo adecuado= Trabajo verificable
Todo lo que rodea al modelo es tuyo, portable y acumulativo. Cambiar de modelo mañana es una línea de configuración; perder tus skills y convenciones sería empezar de cero.
